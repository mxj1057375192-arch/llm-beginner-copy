**现象：训练困惑度一路降到 50，验证困惑度却在 step 200 触底（375）后单调回升。**
这是典型的过拟合：模型开始背训练集里那 15k 个 token，而不是学可迁移的规律。
所以最优模型取在 step 200——**"早停"不是可选项，是这个小语料上的必需操作**。

## 4. 为什么 dev 困惑度到不了 50（关键分析）

我把这个差距量化了一下，结论是：**在 49KB 唐诗语料上，PPL < 50 不现实**，依据有三条。

**(1) 这个语料本身的"不确定性下限"就远高于 50。**
用最简单的 unigram（只看单字频率）模型在训练集上估计：字符熵 **6.40 nats**，对应困惑度 **602**。
也就是说，"完全忽略上下文、只按字频瞎猜"的水平是 602；我们的模型做到 **375**，已经把不确定性降低了 37%，是一个真实有效的语言模型。
要达到 PPL 50，需要把每 token 的交叉熵压到 **3.91 nats** 以下——比 unigram 基线低 2.5 nats，
这需要模型真正掌握句法、对仗、韵脚、意象搭配等深层规律，而 15k token 的语料不足以支撑这种学习。

**(2) dev 里有 6.7% 的字符训练集从没见过。**
dev 787 个字符类型中，104 个（13.2%）未在训练集出现，按出现次数算占 6.67%。
这部分 token 无论模型多大都无法"预测对"，构成困惑度的硬地板。

**(3) 上下文 n-gram 的重复率极低。**
训练集 15k 字符里有 11,742 种不同的字符二元组、14,375 种三元组——几乎每个 n-gram 只出现一次。
模型没有足够重复来估准条件概率，只能记住具体诗句，于是过拟合。

**结论**：阈值 50 是为"更大规模的语料（如 README 提到的 TinyStories 100MB 档）"设定的。
README 也允许小上下文模型跑通流程，并在 M4 卡住时的建议是"先把模型缩小跑通整条 pipeline"——
本报告如实记录：**pipeline 全部跑通，M4 的阈值在 quick-start 唐诗档上未达成**。

### 如果要真正达标，需要什么

| 方案 | 代价 | 预期 |
|---|---|---|
| 换 TinyStories（`python data/download.py --dataset tinystories`） | 下载 ~100MB（实测镜像 37KB/s，约 45 分钟）；英文 BPE 压缩率高，训练更划算 | 数据量 ×1000，收敛明显更好；但官方阈值是 **PPL < 10**，CPU 小模型仍难达到 |

## 5. 消融实验：字节级 vs 字符级 BPE（意外发现）

为了减少"半个汉字的字节碎片"、提高压缩率，我实现了字符级 BPE（基本单位=语料里出现过的字符，
保证每个 token 都是完整字符、无 `<unk>`），并在**完全相同的数据与超参**下对比：

| 词表方案 | 实际词表 | 压缩率 | 单字 token 占比 | 最优 dev ppl |
|---|---|---|---|---|
| byte-level BPE | 2048 | 0.97 字符/token | 12.4%（有字节碎片） | **378.99** |
| char-level BPE | 3206 | 1.11 字符/token | 100% | 1038.44 |

**反直觉的结果：字符级压缩率更高、token 更"干净"，验证困惑度却差了近 3 倍。**
原因在未登录字（OOV）：
- 字符级模型遇到没见过的字，只能从 3206 个候选里瞎猜（它没有"拆字"的能力）；
- 字节级模型可以用已知的字节拼出这个字（比如 dev 的"髓"字=已知的 3 个字节序列），是有依据的推断。

这正好印证了 README「常见坑」里的第一条：**中文按字节级还是字符级要想清楚，字节级的价值在于"永不丢字"**。
在语料小、OOV 多的场景下，这个价值非常实际。

## 6. KV cache 的实测价值（含在 `unit_check.py` 里）

- 等价性：开/关 cache 的 logits 最大误差 **1.9e-06**（自检）/ 2.4e-07（单元自测），数值上完全一致。
- 机制：无 cache 时每步重算整段前缀（总计算量 ~O(T³)），有 cache 时每步只算 1 个新词元 + 一次长度 T 的注意力（~O(T²)）。
- 代码里 `generate.py` 的 `--` 无开关、但 `model.generate(..., use_cache=False)` 可以对比，
  `unit_check.py` 验证了两者在 greedy 下生成结果完全一致。序列越长，cache 的优势越大。

## 7. 生成样例观察（`generation_samples.md`）

固定 prompt「床前明月光」，四种策略的差别非常直观：

- **greedy**：反复输出同一个高频标点，死板（模型小、没有 repetition penalty 时尤其明显）；
- **top-k（k=20）**：从"水、山、春、云、寒、月、风"等高频意象字里选，能凑出像诗的短句，但不成篇章；
- **top-p（p=0.9）**：候选集合随分布自适应，出现更多样但更零碎的字；
- **temperature=1.2**：最"放飞"，会出现低概率字甚至字节碎片（显示为 `�`）。

这组对比能直接说明 M5 的知识点：**采样策略决定了"用什么方式从这个分布里取词"，而分布本身的尖锐程度由训练程度决定**。
本模型训练只到甜点（step 200），分布还很平，所以生成质量有限——这与 §4 的困惑度结论是同一件事的两面。

## 8. 200-500 字实验观察

我实现的是 byte-level BPE + RoPE + KV cache 的 1.12M 参数 mini-GPT，在 49KB 唐诗上训练。
最直观的发现是**验证困惑度在 step 200 触底后持续回升**（375 → 434），而训练困惑度还在往下掉（288 → 50）：
小语料上模型进入"复读机"模式，靠背下具体诗句而不是学规律来降低 loss。
因此我把最优模型取在触底点，这也解释了为什么 README 强调唐诗档要早停。

第二个发现来自词表消融：我用完全相同的超参对比了字节级与字符级 BPE，字符级虽然压缩率更高、token 更干净
（1.11 vs 0.97 字符/token），验证困惑度却差近 3 倍（1038 vs 379）。原因在于 dev 集有 6.7% 的字符训练集没见过：
字节级能用已知字节"拼"出未登录字，字符级只能从 3206 个候选里瞎猜。这让我对"字节级保证无 `<unk>`"
这一设计有了具体的体感，而不只是记住一句话。

第三个发现是 KV cache 的正确性边界：RoPE 增量解码时如果忘了把新词元的位置接在历史长度上，
logits 就会和全量前向对不上。把 `position_offset = 过去长度` 写对之后，两者误差只有 2e-07，
而且 greedy 生成结果逐 token 完全一致——"缓存只是省重复计算，不改变数学结果"这句话被数值验证了。

最后，dev 困惑度没到 50：我算了 unigram 基线（602）和 OOV 比例（6.7%），确认在 49KB 语料 +
纯 CPU 的条件下这个阈值不现实。这是本次未完成的一项，也是我认为最值得继续投入的方向（换更大中文语料）。
